游戏概念​

在Minecraft中，所有元素都具有明确的功能划分。通过决定不同的元素应具有怎样的特性，我们可以快速地按照Minecraft的逻辑添加我们需要的东西。

  • 了解这些逻辑有助于减少不必要的思考并养成良好的编写习惯，还会显著提升代码规范性。

让我们来了解一下不同元素的概念与关系，顺便熟悉一下它们的类名：

在这张思维导图中，我们把Minecraft世界中的不同内容划分成三大板块：

  • 定义(Definitions)：作为定义内容，这些对象在单个Minecraft程序中实际上只有一个实例。

    我们先来逐个介绍一下这些元素。

    • EntityType，即实体类型。村民Villager就是一种实体类型，而制图师、农民，甚至绿袍尊者(bushi)都属于村民类型的实体。

      实体Entity，是实体类型存在于世界中的一个具体实例。每一个生物都是一个单独的实例，通过实例间的变量隔离，同种实体类型的不同实体得以具有相互独立的行动。实体类的构造会被提供给某个实体类型的注册，实体类型通过调用构造产生新的生物实例。

    • Item，即物品。任何你可以拿在手上的东西，比如钻石剑、头盔等，都是物品。手持的方块也属于物品。

      物品在Inventory物品栏中以ItemStack物品栈的形式存储，不同物品不能合并堆叠到同一个物品栈上，同一物品如果属性不同也不能堆叠。

      物品栈被丢出或掉落到世界上的形态是Entity实体，具体来说是继承自Entity类的ItemEntity实例。

    • Block，即方块。方块可以被放置在地上，占据一格空间。

      方块在世界中以BlockState方块状态独立存在，方块状态使得同一个方块能够表现出不同属性，如原木的放置方向、栅栏的连接等。

      在必要情况下，还可以在方块中引入BlockEntity方块实体。方块实体在过去被称为Tile，有些像只能固定在一个格子中的实体。方块实体赋予方块状态存储、自由渲染额外组件和执行工作等丰富的额外功能，当然，代价就是方块实体的运行速度比方块状态慢很多，尤其是作为世界生成的一部分时需要谨慎使用。

      和实体类型与实体的关系类似，方块实体类型BlockEntityType用来构造方块实体实例。

      在以后的章节中，我可能会逐渐开始使用首字母缩写 BE 表示方块实体。不只是BE，很多常用类也会缩写表示，比如负责在物品上渲染方块实体的BlockEntityWithoutLevelRenderer，大家都称呼为BEWLR。

    只有一个实例是什么意思？

    例如，你有两把原版铁镐物品，正作为两个物品堆保留在你的物品栏中，即使它们的附魔不同、耐久度不同、命名也不同，但这两个铁镐在使用时所执行的代码，都指向同一个继承了Item类的实例，也就是PickaxeItem类1，这表明了它们都归属于镐类物品。这一点很重要！（McJty如是说）

    请注意，“只有一个实例” 并不是说所有的镐都共用一个PickaxeItem实例，而是所有木镐共用一个PickaxeItem实例、所有石镐共用一个PickaxeItem实例、所有铁镐共用一个PickaxeItem实例等。物品类本身并非单例，而是给每一种单独注册的物品一个共享实例。

    思考一下：所有的同种物品都指向同一个物品实例，那么它们的变量就是共享的。既然如此，我们是如何区分不同铁镐的名称和耐久度等内容的呢？为什么不能堆叠名称不同的两把铁镐呢？不妨仔细想想这段数据应该由谁来存储。

    有想法了吗？继续阅读获得更多信息吧！

    除了物品，每一种方块、每一种实体类型，以至于每一种方块实体类型，都指向它们唯一的实例。比如所有告示牌都共用名为Sign的方块实体类型，这一方块实体类型作为构造器和工厂，在初始化注册阶段就持有SignBlockEntity类2的new方法入口，在调用时能直接依照参数实例化一个新的SignBlockEntity对象。

  • 物品栏(Inventory)：无论是玩家自己还是其它实体的物品栏，亦或是营火等可以存储**“物品”的方块**，它们所持有的每一组物品都是以ItemStack，也就是物品栈的形式记录在容器中。每一个物品栈，无论容纳着像斧这样只能堆叠一个的物品，还是像草方块物品一样一组最多能堆叠64个的物品，都是不同的实例。

    ItemStack可以看作一种信息容器，记录着这一个栈上对应的物品和它所拥有的独立属性。在玩家使用物品进行交互时，MInecraft会将上游代码中的交互坐标点、玩家属性等参数打包为useContext，再传递给对应Item实例内的方法，并将其返回的交互结果，也就是InteractionResult（可以决定玩家挥手使用的动作是否发生）返回给上游。这一逻辑也辅助着远程玩家行为的同步与计算，节省了网络开支。

    在设计模组时，网络开支也是我们需要深思熟虑的。作为开发者，我们要本着负责任的态度，用心做好每一个模组，不应让网络开销成为其它玩家畅玩MC的绊脚石。

  • 世界内(World)：我们在定义中提到，世界上每一种方块都只有一个实例，也就说明我们只要更改某种方块对应的实例，整个世界的这种方块都会跟着改变。那么，如果这是一个红石灯，我们又如何区分它是亮还是灭呢？红石灯可没有方块实体帮它存储数据。

    实际上，世界中的每个方块都是方块状态，它可以更详细地承载某一个格子内的方块具有什么独立属性。

    当你放下某种材质的台阶时，台阶方块对应的类实例就会被调用。它会判断你放在哪里、哪个平面上以及此刻的你面朝哪里等数据，随后从自身获取一个默认BlockState，并对这个State单独设置属性（你也可以使用调试棒直观地更改它们），随后，该BlockState被Level(世界)放置到坐标上。有关方块放置的相关事件我们会在方块章节再次提到。

    世界中的每个实体类和方块实体类的成员变量都是独立的，但是它们对应的类型，是每种方块唯一的。

用户端​

处理业务的时候，你肯定了解过服务端和客户端。客户端负责处理用户的渲染、交互等显示信息和发出指令的部分，通常运行在使用者的电脑上；服务端则负责处理更新、响应这类数据，一般存在于远程服务器上，也可能在使用者的电脑上。然而，具体来了解Minecraft的用户端机制，会发现Minecraft实际上有两种具体的端类型，分别是物理端组以及逻辑端组。这与标准的双端逻辑略有差异，并有可能会影响到后续的模组开发，需要划分明白。接下来，我会基本按照NeoForge文档的描述，分为物理端组和逻辑端组两种类型进行介绍，并对它们的关系进行阐述。

物理端组​

当你用启动器运行一个Minecraft实例，你其实是启动（boot up）了一个物理客户端。“物理“表示这是一个客户端上的程序。这特别意味着包括所有的渲染功能在内的客户端功能，都可以在这里使用，并且可以根据需要使用。

物理服务端，也被称为专有（dedicated）服务端，是在运行Minecraft服务器Jar时启动的。虽然Minecraft服务器带有基本的GUI功能，但它不具有任何客户端的功能。由此表明，服务器实例中缺少客户端具有的类。在物理服务器上调用这些类将导致类不存在错误(NoClassDefFoundError，是指编译时存在该类，但运行时无法找到)，并会导致崩溃，因此在开发时务必要谨慎对待。

逻辑端组​

逻辑端主要是Minecraft的内部程序结构。

逻辑服务端是执行游戏逻辑的端。像时间和天气变化、实体的游戏刻（game tick）更新和实体生成等操作都在服务端上运行。所有类型的数据，包括物品栏内容数据，也都是服务器该处理的。

逻辑客户端负责控制并渲染所有要在游戏中显示的内容。Minecraft将所有客户端代码保存在一个独立的net.minecraft.client包中，并在一个名为渲染线程（Render Thread）的单独分配的线程中运行，而其它所有逻辑内容都被规定为客户端和服务端共有的代码。

总结​

物理端组代表的是实际上负责调度和运行Minecraft逻辑的进程。你运行一个客户端或一个服务端包的时候，启动的程序体就是物理端程序体

逻辑端组代表的是运行Minecraft游戏逻辑的那部分程序，只负责游戏内逻辑，并在物理端提供的对外界运行环境不敏感的框架内与渲染线程或数据同步机制交互。

关系​

物理端可以调度运行逻辑端，并给逻辑端营造一个无需考虑系统类型的环境，确保在不更改逻辑端代码的情况下适配多种主机。

需要注意的是，在某些情况下，某个端不一定存在。这里是相关情况的例子：

  • 当你启动Minecraft客户端的一段时间内，只存在物理客户端，此时物理客户端正在启动逻辑客户端。
  • 从客户端Minecraft窗体开始渲染开始，只存在物理客户端和逻辑客户端，没有任何服务端可用。
  • 当你加载一个单人游戏存档时，物理客户端开始启动一个逻辑服务端，之后，主机上同时存在物理客户端、逻辑客户端和逻辑服务端，客户端和服务端采用类似localhost(本地连接)的方式传递信息。
  • 当你加入一个多人游戏后，你的主机上只存在物理客户端和逻辑客户端，不同的是你可以和远程服务端进行通信了。
  • 当你启动一个服务端jar的一段时间内，只存在物理服务端，此时物理服务端正在启动逻辑服务端。如果你没有在启动前添加-noGUI参数，物理服务端还将启用一个简易的监控窗口，监视并控制服务器功能。
  • 服务端启动完成后，服务器主机上只存在物理服务端和逻辑服务端。

事件(Events)​

事件系统是NeoForge的一大优秀功能，协助着从模组内容开始按顺序加载到玩家登入、右键、摔落、离开等一系列事件的触发和运行，功能众多，并有效解决了在一般情况下必须要修改源码(Mixin)才能实现某些功能的问题。

事件总线(Event Bus)​

在NeoForge架构中，事件系统是采用总线模式设计的，这个概念是广泛存在于生活中的。

什么是总线​

所谓总线，就是说所有的相关事件发生时都会提交给一个共同的通道，并触发对应该事件的监听器。NeoForge提供两种总线：模组总线(Mod Bus)和游戏总线(Game Bus，也称为NeoForge事件总线)。

当某个事件发生时，程序会在该位置实例化一个具体的Event事件类，不少还携带具体参数，然后把这个事件交给对应BUS并表示：“发生了这样的事情！” 之后，BUS就会在所有已经注册进自己的Listeners中，寻找这个事件的多个对应监听器，再把这个携带信息的事件实例引用传给对应的监听代码块。

这很像你班的体委，开完会后向老师报告道：“体育老师让需要练习长跑的同学现在下楼！”班主任立马点了几个人的名字，告诉他们：“现在下楼，体育老师找你们商量长跑的事情。”

在FML(Fancy Mod Loader)加载模组的阶段，FML会扫描模组代码中的注解，并将收集到的事件注解自动添加到总线。你也可以将事件监听方法或类直接手动注册到总线上。这两种方法都很常见。

⚠️注意

自NeoForge21.1.181起，使用@SubscribeEvent不再需要显示声明使用的BUS类型，这件事我们在后面的文章中会再次提到。

模组总线-Mod Bus​

首先注意一点，FML在模组开始加载时会给每个可加载模组生成并分配一个模组总线，并传给该模组入口方法。值得注意的是，多个模组总线是并发的，也就是同一时刻会有多个模组监听自己的模组总线并执行初始化任务。这种设计使得FML可以更快地加载大量模组。也正是因为并行操作的不确定性，FML不会保证每个模组使用enqueueWork提交的工作3的处理顺序，不过仅对单个模组的提交来说，顺序是正确的。

modBus会作为模组入口类的构造函数的参数，在启动模组时传入。一个最简单的模组入口类，应该长这样：

@Mod(IndustrialHeritage.MOD_ID) // 模组类入口的标记注解，会被FML扫到。
public class IndustrialHeritage { // 模组主类，也叫模组入口类。
    // 一些便于引用的常量，后面会在别的类中使用。
    public static final String MOD_ID = "industrial_heritage";
    // 模组专属名称的Logger，以后的绝大多数输出都会使用这个Logger，便于排查问题。
    public static final Logger LOGGER = LoggerFactory.getLogger("Industrial Heritage");

    // 构造函数，会在FML加载模组时被反射调用。如你所见，ModBus作为参数在这里被传进来。
    public IndustrialHeritage(IEventBus modEventBus, ModContainer modContainer) {
        // 在这里，不同的初始化事件被依次传递注册。
        // 以IH(IndustrialHeritage的首字母)为头，可以使你的模组类在调试期间更具辨识度。
        IHItems.register(modEventBus);
        IHBlocks.register(modEventBus);
        IHEntities.ENTITIES.register(modEventBus);
        IHRegistries.register(modEventBus);
        // ...
    }
}

不用急着写，了解一下结构便可，后面章节的教程中我们会系统性地编写的。

在模组总线上，会依次触发一系列事件，大多数都是ParallelDispatchEvent4这个类的子类。

通常，模组总线也被称为生命周期总线，因为它遵循着一定的生命周期事件顺序：

  1. 模组的入口类执行初始化，向总线注册一系列事件监听器。这一阶段注册到监听器的事件包含模组物品、方块、生物等所有常量的推迟注册表和很多其它初始化事件。当然，还有一部分静态常量在运行过程中被运行时代码触碰而被类加载器加载并完成赋值。
  2. 所有的@EventBusSubscriber均被调用，将声明的事件监听代码段注册到总线
  3. FMLConstructModEvent发生，在总线上广播。
  4. 注册表事件依次发生：NewRegistryEvent和DataPackRegistryEvent.NewRegistry，以及特别的RegistryEvent触发第一步中提交的每个注册表的推迟型内容初始化。
  5. FMLCommonSetupEvent发生，正如其名，这个事件负责启动各种设置初始化。注意Common表示这个行为是每个用户端都有的。
  6. 不同种类用户端的专有事件发生。如果是物理客户端，会发生FMLClientSetupEvent；如果是物理服务端，会发生FMLDedicatedServerSetupEvent。
  7. 处理InterModComms。这是一个很有意思的功能，专门用于模组间互相传递信息。
  8. FMLLoadCompleteEvent发生，标志着整个模组加载阶段的完成。

官方文档还有提到，除了标准的生命周期，另有几个事件因为历史遗留问题（经典一码传三代人走码还在hhh）也会在模组总线上触发，它们包括：

  • RegisterColorHandlersEvent，色彩处理事件，会在处理物品和方块的基本颜色时发生(这个涉及一点着色器相关的内容，我们暂不细究)
  • ModelEvent.BakingCompleted，模型烘焙完成事件。我们在后面写方块的时候会介绍模型烘焙，这里只做一个简单解释——烘焙就是把模型数据转换成能在游戏中展现的实例数据。
  • TextureAtlasStitchedEvent图集拼接完成事件。你需要了解，Minecraft在图像处理上使用了Atlas图集来节省开销。这种行为要求Minecraft把很多方块和物品的单张16x16贴图拼凑成一张巨大无比的图集。在之前使用RenderDoc排查渲染问题时，我还发现实际上他们会给每个模组都生成单独的图集。这也是为什么官方不建议你使用非2^n长宽的照片，因为它会破坏atlas的紧凑性，产生可能微不足道也可能极为严重的额外内存开销。

NeoForge对这些杂七杂八的事件表示：

Most of these events are planned to be moved to the main event bus in a future version.

在未来的版本中，这些事件中的大多数都计划转移到主事件总线上。

嗯，已阅，你们加油。

实际上，NeoForge超级能改造。在我开发这半年期间就遇到了很多曾经用过的功能在更新的版本中被改造的情况。

游戏总线-Game BUS​

这一总线负责处理游戏内事件，包括玩家加入事件、方块交互事件、实体受伤事件、死亡屏幕事件等游戏行为。在合理的需求下注册正确的事件监听能帮助你更轻松地达成目的，但请注意并不是只要能通过事件系统解决就全部塞进事件里，对很多功能的实现，使用总线不是最合适的方案，我们还有更好更快的办法。

注意“不合适”有时候不只是表明在操作上大规模使用事件会拖慢运行速度，还要考虑与原版代码体系相统一的规范性问题。

举一个需要模组作者自己权衡利弊的例子。你希望右键使用物品的时候运行某指令，而实现这个功能有两个办法：

  1. 监听玩家右键事件，从中判断物品是否是目标物品，如果是则截断并返回自己的逻辑，如果不是则正常放行。
  2. 自己注册一个物品类，重写父类use方法并填入逻辑。

这两种方法，各有各的优势。在事件中，你可以截获、计算并改变原版甚至其它模组的物品使用逻辑，这是新建物品类做不到的，使用简易的Item类注册的物品也可以直接判断，无需单独“为一碟醋包一盘饺子”再写一个类。此外，还可以根据不同的匹配规则，对某几类不同类的物品编写统一的功能；但反过来，如果是你已经写过一些物品类继承代码的模组的实例物品，那么使用事件不仅多此一举，还会在使用逻辑中对物品多进行一次判断。另外，当别人因为各种事情来看你的代码时，会按照惯有思维优先去搜索这个物品类而不是右键事件，如果他看到乱堆的代码，可能会短暂地产生一些困惑。

从上面这个例子，我们还能了解到游戏总线的两大核心功用：接管取缔原版逻辑以及进行全局性或跨类群功能改动。

游戏事件的种类繁多，关系链复杂。理论上，当你想去用事件做某些修改的时候，应当想着“这里是不是可以有个事件来允许我这样接管”并在库中搜索相关操作涉及的英文，寻找对应的某某Event类。如果搜不到，也可以直接定位你希望接管的逻辑源代码，看看上下游是否带有NeoForge事件触发的关键代码，从关键代码中寻找事件类。当然，也有不少时候你是根本找不到任何事件的，在这种情况下，如果你需要对原版的功能进行修改或接管，就要轮到我们好几章后才会介绍的Mixin发挥作用了。

注册(Register)​

⚠️警告

嘿！你已经读完了6000字啦！如果感到累了就请先休息一下，因为最后这一部分非常重要！读懂并理解该部分有助于你更清晰地了解模组的运作机制，并避免在不正确的时间注册或访问到未初始化的值。加油！

注册，是使游戏本体得知哪些资源存在且可用的方案。无论是原版元素还是我们模组添加的元素，都离不开注册体系。

有一件事很重要，就是分清注册的几个英文词汇，别搞混了：注册Register、注册表Registry、注册项Registration

在正式开始编写模组之前，我们先来了解一个重要的概念：我们新增的模组元素是如何加载进Minecraft的体系中的。

为什么要注册​

那我问你，如果我写了一篇教程，我不说，也不发出来，你会知道我写了教程吗？

假如你定义了一个静态常量，但没有在别的地方以任何形式使用它，显然MC本身压根就不知道这个常量的存在。

因此，各路加载器都会做的一件事，就是从原版的各路逻辑中牵引出来一部分，在注册的过程中传递内部调用，在MC本体处理同类资源的时候，再把这些东西一并传递给它。因为加载器实际上是一种侵入性修改，不能宽泛地让每个模组人手一个注册时序，否则可能会出大乱子，为此，加载器一并为我们建立了注册体系。

你可能会对模组是怎么加载感到好奇：“没人在MC编译前向MC源码里塞自己的主类，那我的模组怎么跑起来的？” 实际上，这一部分就是加载器在嵌入到原版代码后在运行过程中执行的读取逻辑。当MC启动时，FML系统会去mod文件夹里把所有jar文件~~一把抓住，顷刻炼化！~~挨个读一遍。在处理每个模组时，先确认它具有模组文件该有的格式，前置需求存不存在，随后通过ASM工具库扫描所有文件的方式寻找对应的@Mod、@EventBusSubscriber和@SubscribeEvent等注解（扫读class的过程不属于类加载行为，实际上只是在阅读文件的文本内容），并依据规则对这些类实例化、调用或注册。但是这种注解处理是仅限于最基础的辅助功能，毕竟后面从调用主类初始化方法的那一刻起能干什么可就全随你了。为了诸多代码行事方便，注册系统无疑是最佳之选。

我们将要交互的注册是一个什么概念​

不用往复杂想。完成一个注册只需要理解四个概念：注册表、注册表信息、键和值。

注册表(Registry)其实是一个更高级的Map，本质上就是对Map的封装。它砍掉了clear()、remove()等修改或删除内容的方法来保护注册表，并把put包装成带有注册校验的register方法。在全部元素注册完后，Minecraft会对注册表进行一系列检查，比如检查某些方块是否拥有模型之类的（没有模型信息实际上是不正确的，即使这个方块完全不使用模型，也需要为其填充一个表示空的模型。不过，这种问题最多只会产生一个警告）。

注册表信息就是注册表在Map的封装功能之外额外记录的信息。它并不显示存在于注册元素的代码句中，但是影响着整个注册表的最终注册行为。我们创建一个注册表的时候，会至少被要求填入一个资源键(ResourceKey)，来确认这个注册表可以接受的类和注册表的识别ID。举个简单的例子：

public static final ResourceKey<Registry<Block>> BLOCK_KEY = ResourceKey.createRegistryKey(ResourceLocation.fromNamespaceAndPath(IndustrialHeritage.MOD_ID, "block"));
// 上面这句声明了一个名为block的资源键, 使用它注册的元素都将以industrial_heritage:abc_def...作为其资源坐标
public static final DefaultedRegistry<Block> BLOCK = new DefaultedMappedRegistry<>("stone", BLOCK_KEY, Lifecycle.stable(), true);
// 上面这句创建了一个注册表
public static Block register(String key, Block block) {
    return Registry.register(BLOCK, key, block);
}
// 上面这个方法包装了注册, 简化了最终阶段的代码量
public static final Block TEST_BLOCK = register("test", new Block(BlockBehaviour.Properties.of()));
// 上面这句声明了一个方块并注册, test是它的键名, new Block(...)是它的值

当然，实际上我们注册方块的步骤比这个简单很多（虽然也有更多深层原因），而上面这种更适合于注册自定义元素，马上你就会明白了。

键(Key)就是我们注册一个元素所具有的唯一id，在注册表这里，我们使用字符串。比如minecraft:stone，其中的stone就是一个表示石头的字符串id，该id分别在原版的方块注册表和物品注册表中唯一存在。

值(Value)就是实际进行注册的类。我们之所以能执行营火方块类的行为，是因为在minecraft:campfire这个值背后链接的是一个真正的Block实例，这个实例中写下的各种属性，就是最终作为一个营火方块该表现出来的属性。

正因为是Map的封装，注册表也有一样的特征，同一个注册表中，相同的值只允许被注册一次。对应到实际就是叫做minecraft:stone的石头方块在原版的方块注册表中只有这一个。不过在不同注册表中没有此限制，这也是为什么minecraft:stone在方块注册表中表示石头方块，在物品注册表中还能表示石头物品。

把一切关联起来​

还记得我们上文在游戏概念中提到的单例么？一种方块内的所有方块之所以是同一个实例，就是因为在注册表中它们都对应着同一个键，对应着这个键所代表的值。我们在注册的过程中，也要对实例的注册多一份注意，以免为了图省事先声明实例变量再将其填入不同的注册项中，不然有可能会出现几个方块“量子纠缠”的现象。

在我们能从库中看到官方的一些原版代码里，所有方块都注册在Blocks类内，所有物品都注册在Items类内，所有的实体类型都注册在EntityType类内，所有的方块实体类型都注册在BlockEntityType类内，以后有需要可以直接从这些类中引用。

推迟注册(Deferred register)★​

为什么推迟​

在Minecraft源码中，上文所述的这些注册全部使用了类似

public static final Block AIR = register("air", new AirBlock(BlockBehaviour.Properties.of().replaceable().noCollission().noLootTable().air()));

的注册语句，导致只要有人尝试直接在代码中引用这个注册类，在随后因为类加载规则而进入类加载过程时，在静态初始化阶段(<clinit>，就是常量初始化部分)就会直接注册到注册表中，发生时间点很早5。

为了防止在MC自身的代码体系中发生注册时序问题，MC本体将该过程提到了非常早的时刻，而注册表在注册时序结束后将会被冻结，不允许再次写入新的注册表项。因此，NeoForge为我们额外规划了推迟触碰并统一执行注册的时间窗口。

NeoForge提供了两个工具类用于加载：推迟注册器DeferredRegister和注册事件RegisterEvent。使用推迟注册器无疑是方便的，不过如果你使用了自定义的注册表类型，也可以将它的注册方法加入到注册事件中，在事件触发时随其它注册表一起注册。本质上，推迟注册器就是一个注册事件+注册表的包装。

注册需要的内容​

不同于直接注册，推迟注册表要求我们在注册时传入一个能通过调用get()方法创建并获得实例的Supplier<B>6，或者更完整的Function<ResourceLocation, B>。这是为了保护这些将要被创建的值不会在注册事件发生前进入初始化步骤，并在一定程度上防止循环依赖。直到注册事件发生，它们才会被实例化并注册到注册表。

使用推迟注册表进行注册，会获得一个被DeferredHolder<T, ? extends T>包装的结果，T泛型负责限制我们注册的实例类的父类，比如CampfireBlock的父类是Block，那么使用时就可以写DeferredHolder<Block, CampfireBlock>。当然，直接在限定类上直接使用BlockItem也不会有什么问题，反过来也一样，只是会少一些可以调用的方法和参数。

更加方便？有些小坑~​

对于上面这个情形，会存在一些例外情况。NeoForge为方块和物品的注册提供了更加方便的单泛型包装：DeferredBlock<T extend Block>和DeferredItem<T extend Item>。对于这两个类，若在变量类型中使用DeferredHolder<T, R>进行包容，将只能对T使用Block和Item父级限定符，因为在代码上，这两个Deferred包装类都是继承自DeferredHolder的，而它们在继承中直接定义T为Block或Item，因此T泛型的描述被锁死，不允许使用子类描述作为限定。不过既然都已经有工具了，也不必再用DeferredHolder来描述变量类型了，直接使用对应的DeferredBlock<目标类>和DeferredItem<目标类>就好。

其实DeferredHolder本身使用了Holder<T>和Supplier<T>两个接口，并在重写那个继承自Supplier类的get()方法的时候仅仅是直接调用Holder类的value()方法，所以在操作变量时可以调用这两个方法中的任意一个，且在效果上没有任何区别。对我个人而言，我选择使用get()只是因为把它当作Supplier会更习惯一些（？）。

防止预调用​

我们刚刚提到推迟注册的注册动作是事件触发的，这里就有一个很重要的事情：你无法在注册发生前直接获取Holder中的值。所以不要试图在注册结束之前尝试使用get()或value()，否则你会看到这个报错：

...
Caused by: java.lang.NullPointerException: Trying to access unbound value: ResourceKey[.../...]
...

虽然直接进入流程的get()并不被允许，但使用lambda的流程只要不提前触发都是允许的。比如这样就是一种很常见的写法：

public static final DeferredBlock<Block> EXAMPLE_BLOCK = BLOCKS.registerSimpleBlock("example_block", BlockBehaviour.Properties.of().mapColor(MapColor.STONE));

public static final DeferredItem<BlockItem> EXAMPLE_BLOCK_ITEM = ITEMS.registerSimpleBlockItem("example_block", EXAMPLE_BLOCK);

在这个例子中，EXAMPLE_BLOCK作为Supplier被传入，并在内部代码中确保了访问安全。除此之外，还可以使用：

() -> EXAMPLE_BLOCK.get()

这样的lambda也可以避免在初始化阶段被直接触碰，不过本质上它就是个Supplier的隐式声明。

不过需要注意的是，由于DeferredBlock和DeferredItem除了继承DeferredHolder之外，还实现了ItemLike接口，这个接口会在传递参数时自动适应部分需要Item或ItemLike的输入（在不少代码中，为了方便，如果需要Item实例的话也会一并存在一份使用ItemLike的重载方法），因此这类变量进入到这种方法中，在调用的过程中就会隐式使用get()或get().asItem()方法。务必要小心检查~

防止过晚初始化​

如果你清楚地要在不同类中共用一个DeferredRegister，比如分多个类注册不同的方块来区分不同类别的方块注册，你就可能会遇到这种类型的报错：

Exception caught during firing event: null
...
Caused by: java.lang.IllegalStateException: Cannot register new entries to DeferredRegister after RegisterEvent has been fired.
...

这个报错是“不能在注册事件发生后再向注册器添加新注册项”，一般是因为你在注册时间窗口结束后才执行注册。排除你自己使用了比静态注册晚的方式注册外，还有一个最大的可能——你没有在执行的早期触碰到执行注册的类，导致静态初始化（<clinit>）没有在规定时间内完成，而是在后续代码触碰该类的内容时才开始静态初始化，从而向早已过期的注册器注册内容。

解决的方法也非常简单，当你调用注册的时候，先把所有的注册类摸一遍就好了，像这样：

BlockReg.java
public class BlockReg {
    public static void touch() {
        MachineBlockReg.touch();
    }
    
    public static final DeferredRegister.Blocks BLOCKS = DeferredRegister.createBlocks(IndustrialHeritage.MOD_ID);
    
    public static final DeferredBlock<Block> EXAMPLE_BLOCK = BLOCKS.registerSimpleBlock("example_block", BlockBehaviour.Properties.of().mapColor(MapColor.STONE));
    //...
}
MachineBlockReg.java
import static here.makertechno.industrial_heritage.common.reg.BlockReg.BLOCKS;

public class MachineBlockReg {
    public static void touch() {}
    
    public static final DeferredBlock<Block> EXAMPLE2_BLOCK = BLOCKS.registerSimpleBlock("example2_block", BlockBehaviour.Properties.of().mapColor(MapColor.STONE));
    //...
}
